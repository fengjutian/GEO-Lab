这是一份演示诊断。站点 example.com 是为写作本文虚构的示例，不对应任何真实客户；文中出现的问题类型、数量与页面示例均为构造，用于说明检查流程。本文不包含任何流量、排名、引用率或转化的前后对比，也不对修复效果作承诺。真实诊断需要站点授权、可访问的日志与足够长的观察窗口，这些条件在演示中并不具备。

## 诊断范围与前提

演示假设站点是一个以长文为主的技术博客，约有数百篇公开文章，使用静态站点生成器部署，页面以服务端渲染的 HTML 为主，另有少量由前端脚本注入的目录与相关推荐。诊断只覆盖"内容能否被稳定抓取、解析与引用"的结构层面，不涉及品牌策略、关键词规划与外链建设。

技术诊断与可见性测试是两件事。前者检查的是机器可读性：爬虫能否取到、解析器能否抽出正文、结构化数据是否与页面一致。后者需要在真实问答系统上做重复观测。本文只做前者，因此不能用来说明"这样改就会被 AI 引用"。

## 检查项清单

检查项按"抓取—解析—理解—归因"四级组织，每一项都给出可执行的判定方法，而不是笼统的"建议优化"。

| 检查项 | 判定方法 | 通过标准 |
| --- | --- | --- |
| 抓取可达性 | 用未登录、无 Cookie 的客户端请求，检查状态码与最终 URL | 返回 200 且无意外跳转 |
| 抓取许可 | 读取 robots.txt，核对与站点地图的一致性 | 允许抓取正文，规则无冲突 |
| 渲染依赖 | 禁用 JavaScript 后查看正文是否仍在 HTML 中 | 正文与标题完整可读 |
| 正文抽取 | 用正文抽取工具跑一遍，比对抽出的字数与页面可见字数 | 抽出主体内容，导航与页脚被剔除 |
| 标题层级 | 检查 h1 唯一性与 h2/h3 的嵌套 | 每页一个 h1，层级不跳级 |
| 结构化数据 | 用 schema.org 校验工具检查 Article、BreadcrumbList 等类型 | 必填字段齐全，与页面内容一致 |
| 作者与机构 | 检查作者页、机构页与文章内的署名是否一致 | 名称、链接、简介可互相验证 |
| 时间信息 | 对比页面显示的发布/更新时间和结构化数据中的日期 | 两者一致，时区明确 |
| 内链 | 统计文章到主题页、工具页的链接 | 关键文章可达，无孤立页 |
| 站点地图 | 检查 sitemap 是否包含全部公开文章且 lastmod 合理 | 无 404、无重复、日期不虚高 |

## 发现的问题类型

演示中构造的问题集中在四类，每一类都对应上面的一项或多项检查。

第一类是渲染依赖。目录、代码块高亮与"相关阅读"由脚本注入，禁用 JavaScript 后正文仍在，但小节标题丢失。对以段落为单位的抽取影响有限，对按标题切块的检索管线影响明显。

第二类是结构化数据与页面不一致。Article 的 dateModified 在模板中取的是构建时间，而不是内容实际更新时间，导致所有旧文在每次部署后都显示为"刚更新"。这类问题不会让页面报错，却会污染时效性信号。

第三类是实体不一致。作者在文章页写作"张三"，在作者页写作"Zhang San"，机构名在页脚与关于页使用了两种写法，且缺少指向同一实体的 @id。对读者影响不大，对机器归因是噪声。

第四类是内链结构单薄。大量文章只链向首页与上一篇，缺少指向主题聚合页的链接，导致主题页无法作为"该主题下有哪些文章"的稳定入口。

## 优先级排序方法

优先级不按"问题数量"排，而按三个维度打分：影响面（受影响的页面比例与所处的读取环节）、可验证性（修复后能否用明确的方法确认）、修复成本（模板改动还是逐篇编辑）。三者相乘得到一个粗略序位，再人工复核。

| 问题 | 影响面 | 可验证性 | 成本 | 建议顺序 |
| --- | --- | --- | --- | --- |
| 日期字段错误 | 全站 | 高 | 低 | 1 |
| 实体名称不一致 | 全站 | 高 | 低 | 2 |
| 标题层级缺失 | 多数文章 | 中 | 中 | 3 |
| 内链单薄 | 部分文章 | 中 | 高 | 4 |

把"影响面广、可验证、成本低"的问题排在前面，是因为它们能在短时间内形成可复核的基线，而不是因为它们"最能提升 AI 可见性"。这个排序方法本身也有偏向：它奖励容易被验证的修复，可能低估那些需要长期投入的结构改造。

## 修复建议与验证方式

日期字段应改为读取内容自身的更新时间，并在页面与结构化数据中使用同一来源；验证方法是抽取若干篇已知更新时间的文章，比对页面显示、JSON-LD 与站点地图三处是否一致。实体问题应建立一份作者与机构的规范名称表，为每个实体分配稳定的 @id，并在文章页、作者页、关于页统一引用；验证方法是随机抽取页面，检查名称与 @id 是否唯一且一致。

标题层级应在模板层修复，确保目录由服务端输出的标题生成，而不是由脚本二次注入；验证方法是禁用 JavaScript 后用解析器统计 h2/h3 数量，与编辑器中的标题数量比对，差异应为零。内链改造可以分两步：先让每篇文章至少链向一个主题页，再让主题页按时间或主题聚合文章；验证方法是生成站内链接图，统计孤立页与平均出链数，并在改造前后使用同一脚本对比。

所有验证都应保存原始输出，而不只是"已修复"的结论。结构诊断的价值在于形成可重复的检查记录，而不是一次性打分。

## 局限与后续工作

本演示的局限很明确：站点是虚构的，问题清单来自构造，没有真实日志、没有抓取配额限制、没有多语言与多模板的复杂性。真实站点还会遇到 CDN 缓存、A/B 测试、付费墙与地区屏蔽等变量，这些都会改变诊断结论。后续工作是把同一套检查项脚本化，在一个获得授权的真实站点上跑完整流程，并把"结构修复"与"引用变化"分成两份报告，避免把相关性写成因果。
