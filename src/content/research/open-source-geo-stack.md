GEO 研究经常被简化成"改写内容然后看有没有被引用"。真要做得可复现，中间至少隔着五个环节：把网页稳定地抓下来、把正文从模板里剥离、把检索做对、把嵌入选对、把评测口径定死。开源社区在每个环节都有成熟项目，但没有一个项目能替你决定实验设计。本文按层盘点，只写项目的定位与边界，不比较性能，也不引用任何 star 数或版本号。

## 为什么要自己搭一套工具链

直接用商业 API 做观测，看起来省事，实际上会遇到三个问题。第一，不可回溯。产品的模型与索引随时变化，昨天的结果今天无法复现，而商业接口通常不保留历史版本。第二，不可拆解。你只能看到最终回答，看不到哪些候选被检索、哪些被丢弃，无法判断是内容问题还是检索问题。第三，不可批量。要跑几十个问题、多个系统、多个时段，手工操作无法保证条件一致。

自建工具链的价值不是"更准"，而是"可知"：你知道用了哪个解析器、哪种切块、哪个嵌入、哪版索引，因此结果可以被别人重跑，也可以被自己推翻。

## 采集与解析：先把正文拿干净

采集层的选择取决于目标站点的结构。对静态页面，基于 HTTP 的抓取足够；对依赖前端渲染的页面，需要浏览器自动化。Python 生态里常用的组合是 httpx 或 requests 负责请求、Scrapy 负责调度与去重、Playwright 负责渲染。三者职责不同，不应混为一谈。

解析层的任务是把导航、广告、评论与正文分开。Trafilatura 是这一层最常被提到的项目之一，定位是面向学术与新闻语料的正文抽取与元数据提取，输出纯文本、Markdown 或 XML，适合做后续切块。它的同类包括 readability-lxml 与 newspaper 系列，前者更接近阅读模式算法，后者偏向新闻站点。选择时要注意：正文抽取的召回与精度会直接影响后续所有指标，抽取失败的样本必须被记录，而不是静默丢弃。

一个常被忽略的细节是时间戳。GEO 研究关心内容的时效性，抓取时必须同时记录发布时间、抓取时间与页面上的"最后更新"声明，三者不能互相替代。

## 检索：BM25 与向量检索不是二选一

检索层决定"哪些片段有机会进入生成上下文"。工业界的主流做法是混合检索：稀疏检索负责精确匹配术语与专有名词，稠密检索负责语义相近但措辞不同的情况，再用融合策略合并两路结果。

| 类型 | 代表项目 | 定位 | 注意 |
| --- | --- | --- | --- |
| 稀疏检索 | rank_bm25、Lucene / Elasticsearch / OpenSearch | 词面匹配，可解释，冷启动成本低 | 中文需先做分词，词典影响大 |
| 稠密检索 | FAISS、Qdrant、Milvus、Weaviate、Chroma、LanceDB | 向量近邻搜索，支持过滤与增量写入 | 索引参数与归一化方式影响结果 |
| 混合与重排 | 各向量库自带融合、跨编码器重排 | 合并多路召回，提升前若干条精度 | 重排成本高，需单独评估 |

BM25 不是"过时技术"。在术语密集、查询短、语料领域明确的技术内容上，稀疏检索往往表现稳定，而且它的打分可以解释，便于分析"为什么这段被检索到"。向量库的选择则更工程化：数据量、是否需要元数据过滤、是否要与现有数据库共部署，比"哪个更先进"更重要。

## 嵌入模型：维度不是唯一变量

嵌入模型决定语义空间的形状。Sentence-BERT 把双塔结构用于句向量，使大规模语义检索在工程上可行，这是当前多数嵌入模型的方法源头。此后出现的 BGE、E5、GTE、jina-embeddings 等系列，主要在训练数据、指令前缀与多语言能力上做改进。

选型时真正需要确认的是四件事：是否支持中文与目标领域术语；是否需要查询指令前缀（不少模型要求查询与文档使用不同前缀，漏掉会显著掉点）；最大输入长度是否覆盖你的切块长度；是否允许商用。维度高低与效果没有单调关系，把高维模型直接套在短文本上，往往只是增加存储成本。

还有一个容易踩的坑：换嵌入模型必须重建索引，且旧结果不可与新结果混用。做长期观测时，应把嵌入模型与索引版本写进实验记录。

## RAG 编排：框架解决流程，不解决判断

LangChain、LlamaIndex、Haystack 是这一层最常被引用的项目。它们提供文档加载、切块、检索器封装、提示词模板与链路编排的抽象，能把上述组件串成一条可运行的管线。RAGFlow、Dify 一类项目则更进一步，提供可视化的知识库与工作流界面，适合快速验证想法。

框架的边界需要说清楚：它不会替你决定切块大小，不会告诉你该用哪种融合策略，也不会判断引用是否准确。切块尤其关键。按固定字数切分实现简单，但会把定义与论据切断；按标题层级切分更符合技术文档的结构，但要求原文有清晰的层级。一个实用的折中是"结构优先、长度兜底"：先按小节切，超长再按段落切，并保留标题作为每个块的上下文前缀。

## 评测：公开基准与自有指标要分开

评测层分两类。第一类是公开基准，用于选型：BEIR 覆盖多种检索任务的零样本评测，MTEB 覆盖嵌入模型的多任务评测，二者都提供了可复现的任务定义与数据。第二类是生成侧评测，RAGAS 提供了忠实度、答案相关性、上下文相关性等指标的实现，ir_measures 与 trec_eval 则是信息检索领域的传统评测工具。

公开基准能告诉你"这个模型在平均意义上如何"，不能告诉你"它在你关心的那 20 个问题上如何"。GEO 研究的核心指标——是否被引用、引用在什么位置、引用是否准确——没有现成的开源实现可以直接套用，必须自己定义标注规范并做一致性检验。这也是为什么实验协议要先于工具选型：指标定义不清，工具越强，噪声越大。

## 一个最小可行组合

如果目标是跑通"内容结构变化是否影响引用"的小规模实验，下表是一套成本可控的组合。它不追求最强，只追求每一层都可替换、可记录。

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 采集 | httpx + Playwright | 静态与渲染页面都能覆盖 |
| 解析 | Trafilatura | 正文与元数据一次抽出，输出格式统一 |
| 切块 | 自写脚本，按标题层级 | 逻辑透明，便于做结构变量对照 |
| 检索 | rank_bm25 + 一个向量库 | 先建立可解释基线，再加语义召回 |
| 嵌入 | 支持中文的句向量模型 | 优先确认指令前缀与长度限制 |
| 编排 | 轻量脚本或 LangChain | 链路短时脚本更易审计 |
| 评测 | 自建标注表 + ir_measures | 指标定义先于工具 |

## 局限与后续工作

本文只做定位梳理，没有做任何性能对比，因此不能据此判断"哪个项目更好"。开源项目的维护状态与接口变化很快，本文刻意省略版本号，读者应以项目文档为准。后续工作包括：在同一语料上对比不同解析器的正文召回差异；验证切块策略对引用位置的影响；把评测脚本与标注规范一并开源，使结论可以被独立复核。
