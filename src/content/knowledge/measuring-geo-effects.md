GEO 的效果评估之所以难，不在于缺少指标，而在于输出本身是随机的：同一个问题，不同时间、不同账号、不同地区问，答案与引用列表都可能不同。因此评估的目标不是"某次回答里有没有我"，而是"在一组固定的问题、固定的采样协议下，我的出现概率与出现质量如何变化"。没有采样协议，任何结论都不可复现。

## 先确定要测量什么

评估之前必须区分三类目标，它们的指标不同，混在一起会得出互相矛盾的结论。

第一类是可见性：目标问题下，品牌或域名是否出现、出现在第几位、以什么角色出现。第二类是准确性：回答中关于自身的事实是否正确，例如产品能力、价格、适用边界。第三类是影响：来自生成式引擎的访问是否带来了预期的行为。

多数团队只测第一类，因为它最容易采集。但只测可见性会掩盖一个更危险的问题：被提及但说错了。可见性上升而准确性下降，是负面结果，不是进展。

## 四个核心指标

| 指标 | 定义 | 计算口径 | 常见误用 |
| --- | --- | --- | --- |
| 提及率 | 回答正文中出现品牌名或域名的比例 | 出现次数 ÷ 有效采样次数 | 把推荐列表里的顺带提及等同于主推 |
| 引用率 | 回答的来源链接中包含目标页面的比例 | 含目标链接的采样数 ÷ 有效采样数 | 只统计首页，忽略深层页面 |
| 来源质量 | 被引用时的位置、上下文与角色 | 按位置分层后统计占比 | 只数链接数，不看是否支撑结论 |
| 答案准确率 | 关于自身的事实陈述正确比例 | 正确陈述数 ÷ 涉及自身的陈述总数 | 抽样偏向上线前的问题 |

提及率与引用率要分开统计。品牌可能被提及但没有链接，也可能链接指向第三方报道而非官网。两者的优化手段不同：前者靠实体与内容覆盖，后者靠可抽取的页面与稳定的站点结构。

来源质量需要分层，至少区分三种情形：作为主要依据被引用、作为并列来源之一被引用、仅在延伸阅读中出现。三者对业务的价值差异很大，混在一起求平均会失真。

答案准确率需要人工标注或规则校验。做法是先把回答中涉及自身的事实句抽出来，逐条与官方口径比对，标注为正确、过时、错误、无法判断四类。这一步成本最高，但没有它，前三个指标可能指向错误方向。

## 问题集设计

问题集是评估的地基。它应当来自真实需求，而不是从产品卖点反推。可用的来源包括：站内搜索词、客服工单、销售异议记录、社区提问、竞品对比讨论。

一个可用的集合通常包含四层：

- 品类问题：这个领域有哪些方案，如何选择。
- 品牌问题：某品牌是什么、能做什么、适合谁。
- 对比问题：A 与 B 的差异，迁移成本如何。
- 故障与边界问题：某能力不支持什么，出问题怎么排查。

第四层最容易被忽略，却最能暴露幻觉。生成式引擎在边界问题上更倾向于给出笼统的正面表述，若页面没有明确写出限制，回答很可能过度承诺。

问题数量不必求多。三十到五十个高质量问题，覆盖四层意图，足以支撑趋势观察；扩展到数百个问题而不增加分层，只会放大噪声。

## 样本量与重复观测

单次采样没有解释力。生成过程存在采样随机性，检索索引也在更新，同一问题的结果会漂移。可行做法是对每个问题重复若干次，记录分布而不是单值。

具体次数取决于波动程度：先做一轮小规模预实验，观察同一问题在多次采样中的结果差异，再决定正式观测的重复次数。波动大的问题需要更多重复，稳定的问题可以少一些。关键是所有时间点使用同一套协议，否则前后不可比。

观测应当固定时间窗。例如每周同一天的同一时段执行，避开产品大版本发布与热点事件。跨周比较时，报告的是区间与趋势，不是单点差值。

## 不可比因素

这是评估中最常被忽略的部分。以下因素会让两组数据失去可比性：

- 模型版本更新。底层模型换代后，回答风格与引用策略可能整体改变。
- 产品形态差异。同一家公司的不同入口，检索范围与引用展示方式可能不同。
- 地区与语言。检索结果受地域影响，中文与英文的表现不应混算。
- 登录状态与个性化。登录后可能引入历史偏好，匿名与登录结果不宜直接对比。
- 时间。索引更新、热点事件、竞品动作都会改变候选集。
- 采样参数。温度、上下文长度、是否开启联网，都会影响输出。

处理方式不是消除这些因素，而是记录它们。每次观测都标注模型、入口、地区、时间、是否登录，比较时只取条件一致的数据。

## 观测记录格式

```json
{
  "runId": "2026-11-02-weekly",
  "engine": "example-engine",
  "surface": "web",
  "locale": "zh-CN",
  "loggedIn": false,
  "sampledAt": "2026-11-02T10:00:00+08:00",
  "questionId": "q-017",
  "question": "生成式引擎优化如何衡量效果",
  "samples": [
    {
      "attempt": 1,
      "brandMentioned": true,
      "citedUrls": ["https://example.com/knowledge/measuring-geo-effects/"],
      "citationRole": "primary",
      "factChecks": [
        { "claim": "支持多引擎对比", "verdict": "correct" }
      ]
    }
  ]
}
```

字段设计的要点是：把"问题"与"采样"分开，同一问题下挂多条样本；把"提及"与"引用"分开；把事实核查结果结构化为可统计的枚举值。这样后续才能按问题、按周、按引擎聚合。

## 报告与解读

报告应给出区间而非单点。例如"该问题集下引用率在本周观测中处于某一区间"，比"引用率提升了几个百分点"更诚实。样本量小的时候，差值很可能落在噪声范围内。

同时要报告反例。哪些问题从未被引用、哪些回答出现了事实错误、哪些引用指向了错误的页面，这些信息比总体均值更能指导行动。

最后，评估结论要绑定条件。"在中文、匿名、网页入口、每周一次采样的条件下，引用率上升"是一个可检验的陈述；"GEO 见效了"不是。

## 实践清单

1. 明确评估目标属于可见性、准确性还是影响，不要混算。
2. 建立四层问题集，标注每个问题的意图类型与来源。
3. 先做预实验估计波动，再确定重复次数与观测周期。
4. 分别统计提及率与引用率，来源质量按角色分层。
5. 每次观测记录引擎、入口、地区、登录状态与时间。
6. 报告区间与反例，不报告无法复现的单次截图。
7. 版本更新后重置基线，不与旧数据直接相连。
