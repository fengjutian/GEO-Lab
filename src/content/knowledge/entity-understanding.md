生成式引擎回答一个实体相关的问题时，先要确定问题指向哪个对象，再决定召回哪些页面、抽取哪些句子。页面若不能被稳定地归入某个实体——有明确类型、唯一名称、可核验属性与关系——即使关键词覆盖完整，也很难进入候选集。实体理解因此是 GEO 的前置条件，而不是结构化数据的附加项。

## 实体不是关键词

传统检索把查询和文档都看作词袋，靠词频与共现统计排序。这条路在区分"苹果 股价"与"苹果 热量"时只能依赖上下文词，一旦查询变长、变口语，信号迅速衰减。实体视角换了一个提问方式：这段文本在说哪个对象，它属于什么类型，它有哪些可验证的属性。

一个可用的实体需要四个要素：类型，例如组织、人物、产品、作品、地点或抽象概念；标识，例如知识库中的唯一 ID 或规范 URL；属性，例如成立时间、所在地、作者、版本号；关系，例如隶属于、作者是、区别于、部分包含。缺任何一项，实体就停留在"提及"层面，无法被链接、比较与聚合。

这对写作的直接约束是：一个页面应当有一个主实体，并明确回答"这是什么、属于哪一类、与哪些对象相关、依据是什么"。把三个不相干主题塞进同一页，机器难以判断页面中心，人也会读得吃力。

## 从文本到实体的三段链路

无论具体系统如何实现，实体理解大体可以拆成三步。每一步都有独立的失败模式，且会向下游传导。

| 阶段 | 主要输入 | 期望输出 | 典型失败 |
| --- | --- | --- | --- |
| 提及识别 | 标题、首段、正文、锚文本 | 候选实体串及其位置 | 把行业通用词误判为品牌名 |
| 类型判定 | 上下文修饰语、页面类型、共现实体 | 实体类别与子类 | 类型冲突，把产品写成公司 |
| 消歧链接 | 候选集、上下文、外部标识 | 唯一实体 ID 或规范 URL | 同名实体被错误合并 |

提及识别依赖边界判断。"GEO Lab"是机构名，而"lab"单独出现时只是普通名词；"向量检索"是技术概念，而"检索"是动作。边界错了，后面全部错位。

类型判定依赖上下文与页面模板。同一串字符在新闻页、产品页、文档页里应被赋予不同类别；类型判错会导致实体被挂到错误的父节点下，召回时匹配不到正确的问题集合。

消歧链接是难度最高的一步。它需要外部参照：官方站点、维基数据条目、行业协会名录、GitHub 组织页。缺少外部参照时，系统只能靠上下文相似度猜测，而相似度对同名实体天然不友好。

## 页面如何声明自己讲的是谁

最直接的手段是定义句。首段用"X 是一种……，用于……"的句式，把实体名、上位类型和用途放进同一句。这类句子既方便人快速判断，也是抽取式模型最容易完整切出的片段。

第二是结构化声明。schema.org 定义了 Organization、Person、Article、Product 等类型，JSON-LD 是 W3C 推荐的序列化格式，可放在页面脚本中而不影响渲染。需要明确的是，结构化数据表达的是"页面作者声明了什么"，不是"事实已被验证"。抓取方可以选择读取、忽略，或与页面正文、外部资料交叉验证后采信。

```json
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "name": "GEO Lab",
  "alternateName": "GEO 实验室",
  "url": "https://example.com/",
  "description": "研究生成式引擎优化方法的技术实验室。",
  "sameAs": [
    "https://github.com/example-org",
    "https://www.wikidata.org/wiki/Q000000"
  ]
}
```

第三是一致性。同一实体在关于页、文章作者栏、版权页、社交资料中的名称写法应当统一；sameAs 指向的应是同一实体的其他权威 URL，而不是一堆不相关页面。链接堆得越多、越杂，实体边界反而越模糊。

## 消歧靠的是区分性信息

同名实体是常态，不是例外。一个团队名可能同时是乐队名、开源项目名与公司名；一个产品名可能在不同年份属于不同厂商。系统要区分它们，只能依赖额外的、可核验的限定信息。

可行的做法是在首屏提供区分性上下文：所在地、创始人、成立年份、所属领域、母品牌。这些信息不必挤进标题，但应出现在正文前两段中，并尽量与结构化数据里的字段一致。若页面通篇只有形容词与愿景，消歧就失去了依据。

多语言与缩写是另一类问题。"GEO"在不同语境下可能指地理、生成式引擎优化或某个组织缩写。页面应在首次出现时给出全称与限定语，而不是假定读者与机器都已知晓。

## 常见失败形态

- 品牌名与通用词重合，正文又不给限定语，导致提及被归入通用概念。
- 同一实体在站内有三种写法，标题一种、正文一种、结构化数据再一种。
- 通篇是"领先""赋能""一站式"，没有成立时间、成员、版本、地点等可核验属性。
- 关键定义只存在于图片或视频里，文本层一片空白。
- sameAs 指向搜索结果页或聚合页，而不是实体自身的权威页面。
- 实体页与文章作者栏信息冲突，例如职称、机构名称不一致。

## 实践清单

1. 为每个重要页面确定一个主实体，写出一句话定义，并放在首段。
2. 核对标题、页面主标题、首段、结构化数据中的实体名称是否完全一致。
3. 为 Organization 与 Person 补齐 url、sameAs、description、logo 等字段。
4. 到维基数据、行业目录、GitHub 等第三方来源核对实体是否存在、拼写是否统一。
5. 定期复查实体信息，人员变动、产品更名、域名迁移后及时同步全站。
6. 用"只看首段能否判断这是什么"作为人工验收标准，比数关键词更有效。
