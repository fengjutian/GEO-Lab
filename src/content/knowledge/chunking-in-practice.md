切分（chunking）是 RAG 里最不起眼、却最影响结果的环节。原因很简单：检索以 chunk 为单位发生，一个 chunk 被编码成一个向量，向量的语义被压缩成一个点。块内主题越杂，向量越模糊；块被切在句子中间，语义就越残缺。

## 为什么块大小是一个取舍

块的大小同时影响三件事：

| 块大小 | 召回精度 | 上下文完整度 | 预算占用 |
| --- | --- | --- | --- |
| 很小（< 100 token） | 高：向量主题集中 | 低：论证被切断 | 低：可放更多块 |
| 中等（200–600 token） | 中：常见平衡点 | 中：段落级完整 | 中 |
| 很大（> 1000 token） | 低：多主题混合 | 高：上下文充分 | 高：挤占窗口 |

这不是一个可以“调参解决”的问题，因为三个目标本身就冲突。工程上的经验区间（200–800 token）之所以常见，是因为它通常能让一个自然段完整落入一个块，同时不至于让单块占满上下文预算。

## 四种切分策略

**1. 固定窗口**

按字符或 token 数硬切，配合重叠。实现最简单、长度可预测，但会切断句子、表格与代码块。适合结构混乱的原始文本（例如爬取的网页正文），不适合结构化文档。

**2. 递归切分**

维护一个分隔符优先级列表（标题 → 段落 → 句子 → 空格），先尝试大粒度切分，超长时回退到更细粒度。LangChain 的 `RecursiveCharacterTextSplitter` 是这一思路的常见实现：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=600,
    chunk_overlap=80,
    separators=["\n## ", "\n### ", "\n\n", "\n", "。", "！", "？", " "],
)
chunks = splitter.split_text(document)
```

关键在 `separators` 的顺序：它把 Markdown 标题放在最前面，意味着切分优先发生在标题边界。这不是通用最优解，但对技术文档通常有效。

**3. 结构感知切分**

直接解析文档结构（Markdown AST、HTML DOM、PDF 版面），按章节、表格、列表切分，并对超长小节做二次切分。质量最高，成本也最高，且需要针对文档类型实现。

**4. 语义切分**

对相邻句子计算嵌入相似度，在相似度骤降处断开。思路优雅，但计算成本高、结果不稳定，且对短文档效果不明显。实际生产中多作为结构化切分的补充，而不是替代。

## 重叠比例：10%–20% 通常够用

重叠的作用是让被切断的句子在两块中各出现一次，从而至少有一块保留完整语义。代价是索引冗余与重复召回。

重叠过高会带来一个隐蔽问题：多个高度相似的块同时进入上下文，模型看到的内容几乎重复，信息密度被稀释，而真正不同的信息被挤出预算。

实践中：

- 按句子边界切分时，重叠可以设得很小（0–50 token），因为断点本身就在语义边界上。
- 按固定字符切分时，重叠需要覆盖最长句子的长度，否则无法保证句子完整。
- 重叠应小于块大小的 30%，否则索引size会显著膨胀。

## 父子块：兼顾精度与上下文

一个常见需求是冲突的：检索需要小块（向量准），生成需要大块（上下文全）。父子块（small-to-big）用两层结构解决：

- 索引与检索使用子块（例如 200 token 的句子窗口）。
- 命中后，把该子块所属的父块（例如 1200 token 的小节）放进上下文。

这样检索精度来自子块，生成质量来自父块。代价是索引结构变复杂，且需要维护块之间的从属关系。

```text
文档
└── 父块 A（## 为什么切分重要，约 900 token）
    ├── 子块 A1（前两句，约 180 token）  ← 用于检索
    ├── 子块 A2（中间两句，约 200 token）
    └── 子块 A3（末两句，约 160 token）
```

## 如何验证切分方案

不要用“块数量”或“平均长度”判断好坏。唯一有效的验证是检索命中测试：

1. 准备 20–50 个真实用户问题，覆盖不同意图。
2. 为每个问题人工标注“哪些块包含答案”。
3. 用切分方案建索引，跑查询，计算 Recall@K 与 MRR。
4. 换方案重跑，比较差异。

如果标注成本太高，退一步的做法是：抽 10 个问题，人工检查 top-3 命中块是否包含答案。这比任何理论讨论都可靠。

## 对写作的直接影响

切分策略由工程决定，但切分的**效果**由写作决定。以下写作习惯会直接改善检索：

- **一段一意**：一个段落只讨论一个主题，向量才不会模糊。
- **小节自治**：每个 H2 小节能独立理解，不依赖上一节的代词与前提。
- **结论前置**：小节第一句就是判断句，这一句最可能成为被摘取的片段。
- **避免跨段指代**：少用“上述方法”“该方案”，改用具体名词。

这也是本站文章统一采用“结论先行 + 一段一意”结构的原因：它同时服务于人类阅读与机器切分。

## 小结

切分是在精度与上下文之间找平衡，不存在通用最优参数。可以用本站的 [Chunking 实验](/tools/chunking/) 并排比较固定窗口与标题切分的差异：你会看到，结构边界产生的块长度更不均匀，但每块的语义完整度更高。对内容生产者来说，可控的部分很明确——写的时候就让每个小节自成一段可独立引用的文本。
