GEO 技术诊断经常退化成一张从 SEO 时代继承下来的检查表：有没有 sitemap、有没有 title、有没有结构化数据。这些项仍然必要，但不足以回答一个更基本的问题——当生成式系统要引用这个站点时，链路上会在哪一步断掉。有效的诊断应当沿链路展开，分为可抓取、可理解、可测量三层，每层有明确的通过标准与失败后果。

## 三层框架

第一层是可抓取：抓取端能否稳定、完整地拿到页面内容。这一层失败是硬失败，后面所有优化都无从生效。

第二层是可理解：拿到的内容能否被解析为清晰的实体、主题与结构。这一层失败不会让页面消失，但会让它出现在错误的问题下，或被错误地引用。

第三层是可测量：改动之后能否被观测。这一层失败不影响单次表现，但会让团队无法判断投入是否有效，长期必然导致决策失据。

三层之间是依赖关系，不是并列选项。诊断顺序应当自下而上，跳过第一层直接谈内容优化，是最常见的浪费。

## 第一层：可抓取

robots.txt 是入口。按照 RFC 9309，它是爬虫访问控制协议，不是安全机制，也不具备强制力；规则按最具体匹配生效，`Disallow` 只阻止抓取，不阻止索引已发现的 URL。常见的严重错误包括：误用 `Disallow: /` 屏蔽全站、把 AI 爬虫与搜索引擎爬虫混为一谈而一刀切、在 robots.txt 里写正则或通配符而不确认目标爬虫是否支持。

sitemap 决定发现效率。它应当只包含规范 URL、返回 200 状态、带最后修改时间，并在 robots.txt 中声明位置。一个充满重定向、404 与参数页的 sitemap 比没有 sitemap 更糟。

状态码与重定向链是第三个高发区。超过一跳的重定向、循环重定向、软 404（返回 200 的错误页）都会稀释抓取预算，并让规范判断变得模糊。

canonical 需要与实际返回一致。若 A 页 canonical 指向 B，而 B 又 canonical 回 A，两边都不会被稳定收录。

渲染依赖是最容易被低估的一项。纯客户端渲染的页面，内容是否进入索引取决于抓取端是否执行脚本以及等待时长，这部分不受站方控制。可行的判断方式是抓取原始 HTML，检查正文是否已存在；若不存在，应改为服务端渲染或静态生成。

防火墙与速率限制也会造成误伤。过于激进的 WAF 规则会把正常抓取识别为攻击，表现为间歇性 403 或 429。诊断时应检查是否存在按 User-Agent 的差异化封禁。

## 第二层：可理解

抓取成功之后，问题变成"这段 HTML 在说什么"。检查点集中在语义层。

标题与层级：页面应只有一个主标题，且其文本表达页面主题；`h2` 应对应独立小节，而不是视觉分组。若层级只靠字号与颜色表达，解析端就丢失了结构。

结构化数据：检查 JSON-LD 是否语法有效、类型是否与页面内容匹配、字段是否与可见内容一致。Google 的文档明确要求结构化数据必须描述用户可见的内容，标记与正文不符属于违规，而不是"优化"。

实体一致性：品牌名、机构名、作者名在标题、正文、结构化数据、页脚中是否统一。同一实体多种写法会让消歧失败，进而影响它在实体相关问题下的召回。

语言与地区：`html lang` 是否正确，多语言站点是否用 hreflang 声明对应关系。语言标注错误会导致内容被投放到错误的语言市场。

内链与锚文本：重要页面是否从首页或聚合页可达，锚文本是否描述目标内容。孤岛页面即使质量很高，也很难获得足够的抓取与权重信号。

重复与薄内容：同一主题是否存在多个近乎重复的 URL，参数页、打印页、分页是否处理得当。重复会分散信号，让系统难以选择规范版本。

## 第三层：可测量

这一层决定诊断能否转化为持续改进。需要确认的最小集合是：服务器访问日志是否保留且可按 User-Agent 区分；来源流量是否可以识别生成式引擎的引荐；是否有一套固定的观测问题集与采样协议；改动是否有版本记录。

没有日志，就无法判断抓取频率与抓取错误；没有引荐识别，就只能靠品牌词搜索量间接推测；没有问题集，就只能依赖零散截图。三者缺一，评估都会退化为轶事。

## 检查项清单

| 层级 | 检查项 | 判定标准 | 失败后果 |
| --- | --- | --- | --- |
| 可抓取 | robots.txt | 允许目标爬虫，规则无语法错误 | 整站不被抓取 |
| 可抓取 | sitemap | 仅含规范 URL，全部 200 | 发现效率低，收录滞后 |
| 可抓取 | 状态码 | 无软 404，重定向不超过一跳 | 抓取预算浪费 |
| 可抓取 | 原始 HTML | 正文在首次响应中存在 | 内容依赖脚本，收录不稳定 |
| 可抓取 | canonical | 自指或指向真实规范页 | 规范判断混乱 |
| 可理解 | 标题层级 | 单一主标题，层级连续 | 主题与切块边界模糊 |
| 可理解 | JSON-LD | 语法有效，与可见内容一致 | 标记被忽略或判为违规 |
| 可理解 | 实体一致 | 全站名称、别名统一 | 消歧失败 |
| 可理解 | 语言标注 | lang 与 hreflang 正确 | 投放错语言市场 |
| 可测量 | 访问日志 | 可按爬虫区分，保留足够周期 | 无法定位抓取问题 |
| 可测量 | 引荐识别 | 能识别生成式入口流量 | 效果无法归因 |
| 可测量 | 观测协议 | 固定问题集与采样条件 | 结论不可复现 |

## 快速抓取核查

```yaml
checks:
  - id: robots
    command: curl -s https://example.com/robots.txt
    expect: 目标爬虫未被 Disallow，且声明了 sitemap 位置
  - id: raw-html
    command: curl -s https://example.com/ | grep -o "<h1[^>]*>[^<]*</h1>"
    expect: 返回非空，说明正文在首次响应中已存在
  - id: redirect-chain
    command: curl -sIL https://example.com/knowledge/example/ | grep -E "^(HTTP|location)"
    expect: 单跳以内，最终状态 200
  - id: markup
    command: curl -s https://example.com/ | grep -E "canonical|application/ld\\+json"
    expect: canonical 自指，JSON-LD 块存在且语法有效
```

这段清单只覆盖最基础的几项，但它能在几分钟内区分"内容问题"与"抓取问题"。若 `raw-html` 一项返回空，后续所有内容优化都应当暂停，先解决渲染。

## 从检查到报告

诊断报告的价值取决于能否被行动。一份可用的报告应当包含：断点位置（哪一层、哪个检查项）、影响范围（全站、模板级还是单页）、证据（响应头、HTML 片段、日志记录）、修复建议与验证方式。

避免两种写法：一是把检查表逐项打勾而不给结论，二是直接跳到建议而不给证据。前者无法排序，后者无法验证。

## 边界与不确定性

公开资料没有说明任何生成式系统完整的抓取与引用策略，因此诊断只能覆盖可观测、可验证的部分。像"某个 UA 是否被允许"这类问题，只能通过日志与官方文档推断，不能给出确定答案。

同理，修复一项检查不等于获得引用。诊断的产出是"排除了一个已知的失败可能"，而不是"获得了某个结果"。把这句话写进报告，能避免后续的预期错位。

## 小结

三层诊断的意义在于建立因果顺序：抓不到就没有理解，理解错就没有正确引用，测不到就无法迭代。实践中大多数站点的问题集中在第一层与第二层之间，而讨论往往停留在第三层。先修断点，再谈策略。
